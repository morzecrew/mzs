# RFC 0005 — `enum`: a closed set of shapes, and a `match` that is checked

**Status:** Draft · **Area:** language · **Depends on:** 0002 (to bind fields in arms) · **Audit:** L10, L11

## Summary

`enum Name { A(fields), B, … }` declares a closed set of `record` shapes under one name. A
`match` whose arms are variants of one enum, and which has no `else`, is checked at compile
time: a missing variant is an error. Nothing else is added — a variant *is* a record.

## Motivation

`record` gave shapes a name; programs immediately want "one of these shapes". Today that
is a convention:

```
record Circle(r); record Rect(w, h); record Empty()

fn area(s) {
  match s {
    Circle -> 3.14159 * s.r ** 2
    Rect   -> s.w * s.h
  }                           # Empty falls through: the value is nil, silently
}
```

A `match` with no fitting arm is `nil` (`match 50 { 1 -> "a" }` → `nil`). For open-ended
subjects that is defensible. For "the three kinds of event this program has" it means that
adding a fourth kind produces no diagnostic anywhere — the opposite of how the rest of the
language treats an unanswered question (D16). State machines, parsers and protocol
handlers (`examples/17_state_machine.mzs`) are all this pattern.

## Design

```ebnf
BareStmt   = … | EnumDecl ;
EnumDecl   = "enum" IDENT "{" SEP* Variant { ( "," | SEP+ ) Variant } [ "," ] SEP* "}" ;
Variant    = IDENT [ "(" FieldList ")" ] ;
ExportStmt = "export" ( … | EnumDecl ) ;
```

`enum` is positional, like `record` (§3.5). The declaration hoists (§8.2).

```
enum Shape {
  Circle(r)
  Rect(w, h = w)
  Empty
}
```

**What it declares.**

* Each variant is a `record` in every respect of §7.8: `Circle(2)` is a labelled dict,
  `type(c) == "Circle"`, `c.r`, JSON, equality — unchanged. A variant without a field list
  is a zero-field record; `Empty` names the constructor and `Empty()` builds `{}` with the
  label. (A bare `Empty` in a `match` arm is the shape test, as for any record.)
* `Shape` is bound to a value usable in two places: `x.is("Shape")` is true for any
  variant, and `Shape` as a `match` arm matches any variant. `Shape.variants` is the array
  of variant names. `Shape` is not callable.
* Variant names live in the enclosing scope (like records), so they must be unique in it.

**The checked `match`.** At compile time, a `match` *with a subject* and *without `else`*
whose every arm pattern is a variant of the same enum — bare, or with an RFC 0002 dict
pattern, with or without an `if` guard — must name every variant in at least one arm that
**matches every value of that variant**, and only one arm shape can promise that: the
**bare variant** with no `if` guard (`Circle ->`). A dict-pattern arm never counts, not
even an all-binder one like `Circle {r}`: a variant is an ordinary mutable dict (§7.8),
`c.delete("r")` keeps the `Circle` label, and RFC 0002 says a missing key does not match,
so `Circle {r}` can fall through. Write `Circle {r} -> …` for the values you can
destructure and a bare `Circle -> …` after it, or end with `else`:

```
-e:9:3: syntax: match over Shape does not cover Empty
        (add an arm, or 'else ->' to say the rest is deliberate)
```

The rule is syntactic. It does not need to know the subject's type: it fires because the
*arms* declared what set they range over. A match that mixes variants of two enums, or a
variant and a literal, is unchecked, exactly as today. At run time a checked `match` whose
subject is not a variant **of that enum** — a string that wandered in, or a variant of a
different enum — raises `type: match over Shape got string` (or `… got Color.Red`) instead
of yielding `nil`: the arms claimed to be exhaustive, so there is no honest value to
return.

**JSON.** A variant serialises as its fields, like any record; the label is not content
(§7.8). Round-tripping needs a tag the program chooses (`{kind: "circle", r: 2}`), and
RFC 0002's dict arms are how it is read back. An automatic tag would be a second
serialisation of dicts and is not proposed.

## Compatibility

Additive: `enum Color { … }` is `syntax: unexpected 'Color' after statement` today. The
checked `match` applies only to arms naming variants of an `enum`, which no existing
program has. Depends on audit B4 being settled so that `enum` can be positional.

## Alternatives

* **Warn on every `else`-less `match`.** Far too noisy: `match` as a value-producing ladder
  with a nil fallthrough is idiomatic and specified (§5.5).
* **String enums** (`enum Color { red, green }` → `"red"`). Cheap, but a typo'd string
  compares unequal silently, and there is nothing to carry data. A fieldless variant
  already covers it with a real label.
* **`match!` / `match … exhaustive`** as an explicit opt-in on any match. Needs a keyword
  and still could not know the set without `enum`.

## Open questions

* Should a guarded arm (`Circle if s.r > 0 ->`) count toward coverage? Proposed: no.
* `Shape.parse(dict)` — a generated tagged-JSON reader. Tempting; keep out until asked for.
* Should fieldless variants be values (`Empty`) rather than constructors (`Empty()`)? A
  value reads better; a constructor keeps "a variant is a record" with no exception.

## Implementation

`internal/parser`, `internal/ast` (`EnumDecl`), `mzs/record.go` (variants are records with
an `enum` back-pointer), the compile pass (coverage check), `mzs/builtins.go` (`is`),
printer, LSP outline and completion of missing arms as a code action (RFC 0019).
