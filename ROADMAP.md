# mzs — что нужно языку, чтобы стать полноценным

Разбор пробелов и план работ. Каждая задача написана так, чтобы её можно было отдать
на реализацию целиком, без дополнительного контекста: зачем, что трогаем, как выглядит
результат, что правим в `SPEC.md`, чем проверяем.

**Как отдавать задачу:** «сделай T4» — этого достаточно. Если задача помечена
**«нужно решение автора»**, сначала ответьте на вопрос из её раздела «Развилка»:
она меняет нормативное решение `D…` в спецификации, а такие вещи роадмап сам не решает.

## Инварианты

Любая задача отсюда обязана их сохранить. Это не пожелания — это то, из-за чего язык
выглядит одинаково во всех своих частях.

| # | Инвариант | Откуда |
|---|---|---|
| I1 | `go.mod` без единого `require`. Только стандартная библиотека Go, ни cgo, ни подпроцессов. | G4, A6 |
| I2 | Возможность выключена по умолчанию: новая дырка во внешний мир — это поле в `Options`, а не «оно всегда есть». Единственное исключение уже есть (`http`), второго не заводим без явного решения. | §14.3, D15 |
| I3 | Одно имя у операции. Никаких синонимов, никаких `alias`. Переименование = диагностика did-you-mean. | D17 |
| I4 | `[ … ]` — всегда массив. Смысл `{ … }` определяется позицией и только ею: тело после заголовка, trailing-замыкание после вызова, в операндной позиции — дикт либо замыкание по просмотру §3.12. Ни одна новая конструкция не заводит четвёртого смысла и не требует состояния парсера. | D2, D3 |
| I5 | Неоднозначность — диагностика с подсказкой, а не «молчаливое прочтение». На каждую новую ловушку — своё сообщение в §5.6 и тест. | D16 |
| I6 | UFCS: всё, что добавили как функцию, обязано работать и как метод. | D18 |
| I7 | Скрипт не может уронить процесс хоста: паники ловятся на границе `Run`/`Eval`. | A7 |
| I8 | Одна семантика. Ни режимов, ни диалектов, ни `Options.Compat`. | G3, §9 |

**Definition of done** для любой задачи:

1. `gofmt -l .` молчит, `go vet ./...` чист, `go test -race ./...` зелёный.
2. Раздел в `SPEC.md` дописан/исправлен (номера разделов указаны в задаче), таблица
   стандартной библиотеки пополнена, §20 «reserved» подчищен, если фича оттуда уехала.
3. `README.md`: строка в шпаргалке или абзац в туре — то, что видно новому человеку.
4. Тесты в существующем стиле: юнит рядом с файлом (`*_test.go`), приёмка — в
   `corpus_test.go` (§16), на каждую диагностику — свой кейс (§16.4).
5. Если фича видна в языке — законченный пример в `examples/`, запускающийся сам по себе.
6. Если фича видна снаружи — `editors/vscode/data/api.json` пополнен (он генерируется,
   см. `editors/vscode/data/gen/`).

## Этапы

| Этап | Что закрывает | Задачи |
|---|---|---|
| **M1** | Данные не могут попасть в скрипт. Главный разрыв: `cat log \| mzs -e '…'` сегодня невозможен, потому что stdin — это исходник (`cmd/mzs/main.go`, `source()`). Язык не выполняет собственную цель G1. | T1, T2 |
| **M2** | Дырки в самом языке: то, что чувствуется каждый день (деструктуризация, биты, `ensure`) и то, что упирается в потолок на файлах больше сотни строк (типы, ошибки, лень). | T3–T11 |
| **M3** | Библиотечные пробелы, которые особенно заметны рядом с уже готовым `http`: подписать вебхук нечем, собрать URL нечем. | T12–T15 |
| **M4** | Всё вокруг языка: форматтер, тесты, LSP, раскладка библиотек, обещание совместимости. | T16–T20 |

Рекомендуемый порядок: **T1 → T2 → T3 → T4 → T12 → T5 → T16**. Это закрывает разрыв
между «вычислителем условий» и «языком для терминала», ничего не ломая в грамматике,
кроме T3.

## M1 — CLI перестаёт быть слепым

### T1 — модуль `io`: stdin, файлы, окружение

**Статус: сделано.** Взят вариант **A** (интерфейс `FileSystem` в `Options`). Модуль
`io` — SPEC §12.13 (не §12.8: он оформлен отдельным разделом, как `http`), гейт
`ModuleGate{NeedsFS: true}`, реализации `FileSystem` в библиотеке нет вообще — только у
CLI (`cmd/mzs/fs.go`). Заодно сделан пункт 1 из T2 (`source()` отдаёт stdin в
`Options.Stdin`, когда исходник пришёл из `-e` или файла): без него половина модуля в
единственном хосте репозитория была бы мертва, а сам пример её обещает. Флаги `--io`,
`--no-io`, `--in`, `-n`, `-l` ушли в T2 и там сделаны.

**Размер:** M · **Зависимости:** нет · **Нужно решение автора:** да (см. развилку)

**Зачем.** Скрипт не может прочитать ни байта данных. `read`, `gets`, `$STDIN`, `File`,
`ENV` — ничего этого нет (проверено по всем регистрациям в `builtins.go`, `str.go`,
`array.go`, `dict.go`, `num.go`, `methods.go`). Данные попадают внутрь только через
`-v/--vars` и `$ARGV`. Для встраивания в бота это правильно и должно таким остаться;
для CLI это отрезает весь класс задач, ради которых однострочник и существует.

**Развилка.** Как хост отдаёт файловую систему:

- **(A, рекомендую)** По образцу `ModuleLoader`: интерфейс в `Options`, реализацию даёт
  хост. Тогда бот может подсунуть виртуальную ФС или не дать ничего, а CLI отдаёт
  настоящую. Сохраняет I2 и стиль, который в проекте уже есть.
- (B) Поле-флаг `EnableIO bool` и жёстко зашитый доступ к реальной ФС. Проще, но хост
  теряет контроль над политикой, и §14.3 придётся переписывать сильнее.

**Объём (вариант A).**

```go
// options.go
type FileSystem interface {
    Open(name string) (io.ReadCloser, error)
    Create(name string) (io.WriteCloser, error)  // + Append
    Stat(name string) (exists bool, size int64, dir bool, err error)
    List(dir string) ([]string, error)
}

type Options struct {
    // …
    FS    FileSystem            // nil — модуль io не установлен вовсе
    Stdin io.Reader             // nil — io.stdin/io.lines дают ""/[]
    Env   func(name string) string // nil — io.env всегда nil
}
```

Модуль (регистрируется как `http` — см. `http.go`, `RegisterModuleFunc` в `methods.go`):

| Член | Сигнатура | Семантика |
|---|---|---|
| `io.stdin` | `-> string` | весь stdin один раз, кэшируется на Run |
| `io.lines` | `-> array` | `io.stdin.lines`; ленивый вариант приедет в T10 |
| `io.read` | `(path: string) -> string` | ошибка скрипта при неудаче, ловится `try` |
| `io.write` | `(path: string, s: string) -> int` | вернуть число записанных байт |
| `io.append` | `(path: string, s: string) -> int` | |
| `io.exists` | `(path: string) -> bool` | |
| `io.ls` | `(dir: string = ".") -> array` | имена, отсортированы (детерминизм, §8.13) |
| `io.env` | `(name: string, default: any = nil) -> string \| nil` | |

**Файлы.** `io.go` (новый) + `io_test.go`, `options.go`, `interp.go` (установка модуля по
наличию `FS`), `SPEC.md` §12.13 (раздел модуля) и §12.8 (таблица модулей), §13.2 (Options), §14.3 (песочница —
переписать абзац «no File, no ENV»), `README.md` (стандартная библиотека, песочница).

**Границы.** Никакого `system`/`exec` — это остаётся вечным non-goal (§20). Размер
чтения ограничен `MaxStringBytes`. Пути хост резолвит сам, скрипт не может выйти за
пределы того, что дал хост, — ровно как с `ModuleLoader`.

**Готово когда.** `mzs -e 'include io; io.read("/etc/hostname").trim'` работает из CLI и
падает с внятной ошибкой «хост не включил io» во встроенном интерпретаторе с нулевыми
`Options`.

### T2 — CLI: данные через пайп, `--io`, `-n`/`-l`

**Статус: сделано.** Флаги: `-n, --for-each-line`, `-l, --print-each-line`, `--in <path>`,
`--io`/`--no-io`. Решения, которые пришлось принять по дороге и которые записаны в
SPEC §15:

- каждая строка — **отдельный прогон** (`*Program` неизменяем, у каждого прогона свой кадр),
  поэтому свой таймаут и свой бюджет шагов на строку;
- `$переменные` переезжают со строки на строку — CLI возвращает `Result.Globals` во вход
  следующей строки, и `$n = ($n ?? 0) + 1` считает; локальные не переезжают. Это и делает
  `-n` обещанным «сахаром над одним циклом», а не просто N независимыми запусками;
- `--bool` под `-n` — вопрос grep: `0`, если истинной оказалась **хоть одна** строка;
  досрочного выхода нет, иначе вывод программы зависел бы от места первого совпадения;
- под `-n` читателем владеет CLI, поэтому `io.stdin` пуст: строка лежит в `$_`;
- `-n` без данных (программа сама пришла из stdin) — ошибка в аргументах с подсказкой
  про `--in`, а не тихий прогон по нулю строк;
- `--no-io` забирает `FS`, `Env` и `Stdin` разом, но не `-n`: строки читает CLI.

**Размер:** S · **Зависимости:** T1

**Зачем.** Даже с модулем `io` пайп остаётся сломанным: `source()` в `cmd/mzs/main.go`
читает stdin как **исходник**, когда он не терминал. С `-e` исходник берётся из флага —
значит stdin свободен и должен становиться данными.

**Объём.**

1. ~~`source()`: если заданы `-e`/файл — stdin не трогать, отдать его в `Options.Stdin`.
   `cat s.mzs | mzs` (без `-e`, без файла) продолжает читать исходник — это поведение
   документировано и ломать его не надо.~~ **Сделано в T1** (`cfg.stdinIsSource`).
2. ~~Флаги: `--io` / `--no-io` (включить/выключить модуль; для CLI по умолчанию **включён**,
   так как CLI сам себе хост), `--in <path>` — подменить stdin файлом.~~
3. ~~Построчные режимы, ради которых жанр и существует:
   - `-n` — выполнить программу для каждой строки stdin, строка доступна как `$_`;
   - `-l` — то же плюс печатать значение каждой итерации, если оно не `nil`.
   Обе — сахар над одним циклом на стороне CLI, не новая семантика языка.~~

**Файлы.** `cmd/mzs/main.go`, `cmd/mzs/*_test.go`, `SPEC.md` §15 (таблица флагов),
`README.md` (раздел CLI).

**Готово когда.**

```sh
ls | mzs -e 'include io; io.lines.filter { it.ends_with(".mzs") }.len'
```

## M2 — язык

### T3 — деструктуризация

**Статус: сделано.** SPEC §8.15 (новый раздел в конце §8 — так §8.14 и все ссылки на него
не поехали), §4 (грамматика), §5.3 (таблица паттернов), §6.1/§6.2 (узлы и десахаринг),
§16.4, §20. Новых лексем нет, `internal/lexer` и `editors/vscode/data/api.json` не тронуты.
Решения, которые пришлось принять по дороге:

- **Две записи, одна семантика.** Голая `a, b = xs` — только на уровне оператора
  (запятая на нулевой глубине скобок означает другое внутри вызова, коллекции, заголовка
  `for` и ветки `match`); `[a, b] = xs` — обычное выражение и работает везде. Первую ловит
  ограниченный просмотр по токенам (`destructureAhead`, в духе §3.12), вторую — сам
  `parseAssign`: слева от `=` уже лежит `ArrayLit`, потому что `[` всегда массив (D3).
- **Диагностика несовпадения — не в §5.6.** Раздел §5.6 — про неоднозначности разбора
  (паста из Ruby), а `a, b = 1` падает на исполнении. Поэтому таблица ошибок живёт в §8.15,
  а именованные кейсы — в `corpus_test.go` (`TestDestructureMismatch`, §16.4). Виды:
  длина — `index`, не-массив — `type`.
- **Ветка `match`: имя связывает, всё остальное сравнивается** (regex — матчится), позиция
  за позицией. Это сохраняет старый смысл `[1, 2] ->` (сравнение с литеральным массивом:
  поэлементно результат тот же) и делает задачу расширением, а не поломкой — меняется
  только ветка, написанная именами. Проход по `examples/` и `testdata/` таких не нашёл.
- Паттерн-массив **должен быть единственным в ветке** («или» над паттернами, связывающими
  разные имена, телу опереться не на что) и **требует subject** — без него каждый паттерн
  просто условие (§5.4). Имена живут в области видимости ветки, поэтому guard их видит,
  а после ветки их нет.
- **`for k, v` подтянут к тому же правилу** и это единственное ужесточение: раньше элемент
  не-пара давал `v = nil` и лишние элементы молча терялись, теперь это ошибка выполнения.
- Составные операторы не деструктурируют: `a, b += xs` — диагностика, а не догадка.
  `=` и `:=` работают позиционно ровно как поодиночке (§8.2).
- «Остаток» не сделан, как и планировалось: в §20 от деструктуризации остался только
  `a, *rest = xs`, зарезервированный вместе с `*splat` в точке вызова.

**Размер:** M · **Зависимости:** нет

**Зачем.** Самая заметная дырка в эргономике; место под неё уже расчищено в §20, и
именно из-за неё паттерн-массив в ветке `match` сегодня требует префикса `in` (§5.3).

**Объём.**

```
a, b = pair                      # массив из двух
a, b = [1, 2, 3]                 # ошибка: длина не совпала
name, price = [dict.name, dict.price]
match order { [x, y] -> x + y; else -> 0 }     # без `in` — это деструктуризация
for k, v in d { … }              # если for уже поддерживает пару — привести к одному виду
```

Решения, которые надо принять и записать в SPEC:

- несовпадение длины — **ошибка выполнения**, а не молчаливый `nil` (I5 в духе D16);
- работает по Array и Range; по Dict — нет (порядок ключей — не позиционный контракт);
- вложенность `[a, [b, c]] = …` — да, рекурсивно;
- «остаток» (`a, *rest`) — **нет** в этой задаче: `*splat` зарезервирован отдельно.

**Файлы.** `internal/parser/parser.go` (левая часть присваивания, паттерны веток),
`internal/ast/ast.go` + `walk.go` (узел `DestructureAssign`, паттерн `ArrayPattern`),
`eval.go` (исполнение), `internal/lexer` — не трогаем, новых лексем нет.
`SPEC.md` §4 (грамматика), §5.3 (паттерны), §6.1 (узлы), §8 (семантика), §20 (убрать из
зарезервированного). Диагностика для `a, b = 1` («правая часть не массив») — в §8.15 и
в `corpus_test.go` §16.4.

**Риск.** Ветка `match` с массивом меняет смысл: сегодня `[x, y] ->` — ошибка разбора,
после задачи — паттерн. Это расширение, не поломка, но пройтись по `testdata/` и
`examples/` обязательно.

### T4 — битовые операции

**Статус: сделано.** Взят рекомендованный вариант — функции, а не операторы:
`band` `bor` `bxor` `bnot` `shl` `shr` `popcount` `bit` (глобальные builtin'ы в `num.go`,
методами становятся сами собой по UFCS) плюс `array.pack_bytes` в `array.go`. SPEC §12.5
(подтаблица «Bit operations»), §12.3 и §12.2 (`bytes` ↔ `pack_bytes`), §3.9, §5.6, §16.4,
§20. Новых лексем нет. Решения, которые пришлось принять по дороге:

- **`&`, `|`, `^` получили свои диагностики** — этого в задаче не было, но без них I5 не
  выполняется: человек, пришедший из другого языка, пишет `flags & 0xff` и до сих пор
  получал «unexpected character». Теперь это три строки в §5.6 («use band(a, b), or '&&'
  for logical and» и так далее), рядом с уже жившим там `&.`. Ловит лексер: ни один из
  трёх рунов не является токеном, парсер их не видит. `<<`/`>>` не тронуты — остаются
  зарезервированными за §20 и heredoc'ом из T8, сдвиг зовётся `shl`/`shr`.
- **Аргумент строго `int`.** `2.9.band(1)` — ошибка типа с подсказкой `x.int`, а не тихое
  усечение: §9.1 не знает коэрсии, а «биты числа 2.9» не имеют защитимого ответа. Это
  строже, чем `argInt` у остальной библиотеки (она принимает и Float), поэтому у битовых
  строк свой `argBits`.
- **Отсутствие промоции записано явно** (тонкость из задачи): `shl(1, 63)` — самый
  отрицательный int64, `shl(1, 64)` — `0`, тогда как `2 ** 64` уезжает во Float. Это
  вынесено в §12.5 отдельным абзацем и в §16.4 (`TestBitOpsStayInt`), потому что иначе
  D9 читается как обещание, распространяющееся и сюда.
- **Отрицательный сдвиг — ошибка, а не сдвиг в другую сторону**, и счётчик больше 63
  насыщает (`0`, а для `shr` отрицательного — `-1`), а не заворачивается. Индекс в `bit`
  вне `0..63` — тоже ошибка: у отрицательного числа все биты выше 63 — единицы, так что
  любой ответ был бы догадкой.
- **`pack_bytes` работает в байтах, а не в рунах**, и может собрать строку, которая не
  является валидным UTF-8, — ровно как `io.read` двоичного файла (§12.13). Валидация
  только на 0..255, с номером элемента в сообщении. Строка живёт на KArray *и* KRange
  (`(65..70).pack_bytes`), потому что это чистая по receiver'у строка.
- Пример — `examples/34_bits_and_bytes.mzs`: флаги, маски RGB, IPv4 и проверка подсети,
  `bytes`/`pack_bytes`, CRC-32 на двенадцати строках и отказ функций гадать.
- **Заодно убраны строки `&`, `|`, `^` у bool** (`builtins.go`): §12.9 прямо говорит, что
  `&&`/`||`/`!` — весь набор, `&` не лексема (§3.9), а после `.` идёт идентификатор, —
  то есть это были вторые имена для `&&`, дозвониться до которых мог только Go (D17).
  Всплыли на ревью PR: они протекали в `api.json` как недокументированные методы, и
  соседство «`&` не оператор» в диагностике с «`&` — метод bool» в реестре читалось как
  противоречие. Тест в `builtins_test.go` теперь охраняет их отсутствие.

Не сделано и сделано не будет в рамках задачи: варианты `band(a, b, c)` (одна форма — два
аргумента), беззнаковый сдвиг (`shr` арифметический, это записано), `rotl`/`rotr`.

**Размер:** S · **Зависимости:** нет

**Зачем.** `&`, `|`, `^`, `<<`, `>>` не являются лексемами вовсе (§3.9), функций-замен
нет. Флаги, маски, хэши, разбор бинарных форматов — весь класс задач закрыт. `bytes`
у строки есть, а собрать из байтов число нечем.

**Решение (рекомендую).** Добавить **функции**, а не операторы. `&` и `|` рядом с
`&&`/`||` — ровно тот случай, который D16 велит не заводить, а `<<`/`>>` зарезервированы
под другое. Функции же попадают в общий namespace и по UFCS сразу работают как методы.

| Имя | Сигнатура | |
|---|---|---|
| `band` `bor` `bxor` | `(a: int, b: int) -> int` | `flags.band(0xff)` |
| `bnot` | `(a: int) -> int` | |
| `shl` `shr` | `(a: int, n: int) -> int` | `shr` — арифметический сдвиг (int64) |
| `popcount` | `(a: int) -> int` | |
| `bit` | `(a: int, i: int) -> bool` | проверка одного бита |

Плюс обратное к `bytes`: `array.pack_bytes -> string` (валидирует 0..255) — иначе
`"…".bytes` остаётся улицей с односторонним движением.

**Файлы.** `num.go` (+ `pack_bytes` в `array.go`), `num_test.go`, `SPEC.md` §12.5,
`README.md`, `examples/` — короткий пример с флагами или CRC.

**Тонкость.** `Int` — это `int64`, и D9 говорит, что переполнение промотит во `float`.
Битовые функции обязаны работать в чистом `int64` без всякой промоции — записать это
в SPEC явной строкой.

### T5 — `ensure` и блочный `try`

**Размер:** M · **Зависимости:** нет

**Зачем.** `try X else Y` есть, гарантированного освобождения нет. С http-сервером,
файлами (T1) и задачами это уже нужно. Блочный `try { … } else { … }` зарезервирован
в §20 и добавляется как сахар без конфликта в грамматике — ровно потому, что `{ … }`
это замыкание (D2).

**Объём.**

```
try { a; b } else { "-" }
try { a } else (e) { e.message }
try { open() } ensure { close() }
try { … } else { … } ensure { … }
```

`ensure` выполняется всегда: и на нормальном выходе, и при `raise`, и при `return`/`break`
из тела. Что он **не** ловит — то же, что и `try` (§8.11): таймаут, бюджет шагов, предел
глубины, отмену контекста. Записать это явной строкой, иначе `ensure` начнут считать
средством пережить таймаут.

**Файлы.** `internal/parser/parser.go`, `internal/ast`, `eval.go`, `errors.go`,
`SPEC.md` §4, §8.11, §20 (убрать из зарезервированного), `errors_test.go`,
`corpus_test.go`. Ключевое слово `ensure` добавляется в список §3.5 — это единственное
пополнение из четырнадцати, и его стоит отметить в README.

### T6 — ошибки с видом, `match` по ошибке

**Размер:** M · **Зависимости:** T5 (лучше вместе) · **Нужно решение автора:** да

**Зачем.** Сегодня `try … else (e) -> …` даёт dict `[message, kind, line]`. Отличить
«битый JSON» от «нет ключа» можно только сравнением строк, а `kind` нигде не
перечислен как закрытое множество. Это делает `try` пригодным для «не упасть» и
непригодным для «обработать по-разному».

**Объём.**

1. Закрытый список видов в SPEC: `type`, `name`, `index`, `key`, `arg`, `zero_division`,
   `json`, `http`, `io`, `limit`, `user`. Каждое место, где рождается ошибка, ставит свой.
2. `raise("msg", kind: "user")` и `raise({message: …, kind: …, data: …})` — второе уже
   почти есть (`raise(dict)` цепляет `data`).
3. Матчинг: `try f() else (e) { match e.kind { "json" -> …; "io" -> …; else -> raise(e) } }`.
   Для этого нужен **перевыброс**: `raise(e)`, где `e` — dict ошибки, обязан сохранять
   позицию и стек исходной, а не подменять их точкой перевыброса.

**Развилка.** Оставить ошибку словарём или завести отдельный вид значения `error`
(`type(e) == "error"`)? Словарь дешевле и уже работает; отдельный вид честнее и
позволяет `is("error")`. Рекомендую **остаться на словаре** — новый вид значения тянет
за собой §7.1, JSON-сериализацию, равенство и хэширование, а выгода мала.

**Файлы.** `errors.go`, `eval.go`, все места с `nameErrorf`/`ArgErrorf`, `SPEC.md`
§8.11, §17 (диагностики), `errors_test.go`, `corpus_test.go`.

### T7 — записи (`record`)

**Размер:** L · **Зависимости:** T3 (деструктуризация записи) · **Нужно решение автора:** да

**Зачем.** Всё — dict. В `examples/27_lib_money.mzs` это значит: нет проверки формы, нет
`type(x)` для домена, «деньги» неотличимы от пары чисел. Для скрипта на двадцать строк
нормально, для библиотеки — потолок.

**Решение.** Не классы. Именованная форма поверх уже существующего dict:

```
record Money(amount, currency)

m = Money(1500, "RUB")
m.amount                 # 1500
type(m) == "Money"
m.is("dict") == true     # это по-прежнему dict: json, keys, dig работают как раньше
Money(1500)              # ошибка: не хватает аргумента currency
match m { Money -> …; else -> … }
```

Инварианты, которые это сохраняет: `[ … ]` не получает третьего смысла (I4), никакого
наследования, никаких методов на типе — функции остаются свободными и достаются по UFCS
(`fn plus(m: Money, n) { … }` — если типизация параметров вообще появится; в этой задаче
её нет).

**Развилка.** Записи неизменяемы (`with`-обновление даёт новую) или это обычный dict,
который можно мутировать `set`? Рекомендую **обычный dict с меткой типа** — дешевле и
не заводит второй модели изменяемости.

**Файлы.** `internal/lexer` (ключевое слово `record`), `internal/parser`, `internal/ast`,
`eval.go`, `value.go` (метка типа в dict — поле рядом с порядком вставки, см. `odict.go`),
`json.go` (метка не должна протечь в JSON), `SPEC.md` §7 (модель значений), §4, §12.4.

### T8 — heredoc

**Размер:** S · **Зависимости:** нет

**Зачем.** Многострочный шаблон, SQL, HTML, текст сообщения бота — писать нечем, кроме
конкатенации с `\n`. Зарезервировано в §20 как `<<~HEREDOC`.

обязан продолжать читать **строки после текущей**, а не с места токена. Это главный
источник ошибок в такой фиче; тест на heredoc внутри списка аргументов обязателен.

### T10 — ленивые последовательности

**Размер:** L · **Зависимости:** T1, T2

**Зачем.** Всё материализуется: `range`, `lines`, `each_slice` без блока строят массив
целиком, `MaxCollection` ограничивает это миллионом элементов. Лог на гигабайт не
обработать — а после T1/T2 именно это и попросят.

**Объём.** Отдельный вид значения `seq` — ленивый источник с `map`/`filter`/`take`/
`take_while`/`drop`/`each`/`reduce`, материализация только на `.array`, `.sum`, `.len`,
`.join` и подобных «терминальных» шагах. Источники: `io.lines`, `range` (лениво, если
границы велики), `seq` из замыкания-генератора.

**Тонкости, из-за которых это L, а не M:**

- бюджет шагов и таймаут должны тикать внутри ленивой цепочки, иначе бесконечный `seq`
  становится способом обойти §14.1;
- `seq` не сериализуется в JSON и не сравнивается — записать в §7.4/§7.6 явно;
- `type(s) == "seq"`, но `is("array")` — **false** (в отличие от Range, §12.10), иначе
  хост-код начнёт принимать одно за другое.

**Развилка.** Можно вместо ленивых последовательностей дать просто потоковый
`io.each_line { … }` — 10% работы, 80% пользы для однострочников. **Если время дорого,
делайте это, а T10 отложите.**

### T12 — модуль `hash`: hex, base64, sha, hmac

**Размер:** S · **Зависимости:** нет

**Зачем.** Самый заметный практический пробел: `http` умеет и сервер, и клиент, а
подписать или проверить вебхук нечем. В коде нет ни `base64`, ни `hex`, ни `sha256`,

| Член | Сигнатура |
|---|---|
| `hash.hex` / `hash.unhex` | `(s: string) -> string` |
| `hash.base64` / `hash.unbase64` | `(s: string, url: bool = false) -> string` |
| `hash.sha256` / `hash.sha1` / `hash.md5` | `(s: string) -> string` (hex) |
| `hash.hmac` | `(key: string, msg: string, alg: string = "sha256") -> string` |

**Имя.** В §12.1 уже есть функция `hash(x)` (FNV-1a). По правилу §12.8 включение модуля

подсказкой — это ровно тот механизм, что уже описан для `json`. Либо так, либо назвать
модуль `crypto`. **Рекомендую `crypto`** — меньше сюрприза, и содержимое честно про это.

**Файлы.** `crypto.go` (новый) + тесты, `SPEC.md` §12.8, `README.md`, `examples/` —

### T15 — Unicode: `normalize`, `casefold`, ширина

**Размер:** S · **Зависимости:** нет · **Внимание:** I1

**Зачем.** Язык гордится рунной корректностью, но `"й"` в NFC и в NFD не равны, а

```
include test
test.case("нормализация") { assert("  ДА ".lower.trim == "да") }
test.eq(actual, expected)          # сообщение о расхождении показывает inspect обоих
```

`mzs test [каталог]` находит `*_test.mzs`, гоняет каждый файл своим Run (изоляция уже
есть), печатает отчёт, код возврата 1 при падении. Таймаут на файл — из общих `Options`.

**Файлы.** `test.go` (модуль) + `cmd/mzs/main.go` (подкоманда), `SPEC.md` §12.8, §15,
`examples/` — тест к `27_lib_money.mzs`.

### T18 — `mzs lsp`

**Размер:** L · **Зависимости:** T16 (форматирование через LSP)

**Зачем.** В `editors/vscode` есть грамматика, сниппеты, иконки и `data/api.json` — то
есть подсветка и автодополнение по списку, но не по программе. Диагностики компилятора
(а они в этом языке лучшая его часть) в редакторе не видны.

**Объём по убыванию пользы:** диагностики при сохранении (это уже `--check`, надо лишь
завернуть в LSP) → hover с сигнатурой из `api.json` → go-to-definition для `fn` и
`include` → автодополнение по области видимости → форматирование документа (T16).

**Файлы.** `cmd/mzs/lsp/` (новый; JSON-RPC поверх stdio пишется на голом
`encoding/json` — I1 сохраняется), `editors/vscode/src/extension.js` (запуск сервера).

### T19 — разрешение модулей и раскладка библиотек

**Размер:** M · **Зависимости:** нет

**Зачем.** `include lib from "./lib.mzs"` идёт через `Options.ModuleLoader`, и это
правильно для встраивания. Но для CLI нет ни путей поиска, ни способа переиспользовать
библиотеку между проектами: каждый файл ссылается на соседа относительным путём.

**Объём.** Только на стороне CLI, ядро не трогаем:

1. `MZSPATH` (разделитель — `os.PathListSeparator`) и `~/.mzs/lib` по умолчанию;
2. `include money from "money"` без `./` ищет по этому пути, с `./` — только рядом
   с файлом (как сейчас, `includeRoot` в `main.go`);
3. запрет выхода за корень остаётся: `../../..` наружу — ошибка, а не чтение.

**Файлы.** `cmd/mzs/main.go`, `SPEC.md` §12.8 (абзац про CLI-загрузчик), §15, `README.md`.

**Не в этой задаче.** Менеджер пакетов, версии, реестр. Сначала пути поиска — этого
хватает на годы, а реестр требует ответа на вопрос «кто хостит», которого пока нет.

### T20 — версионирование языка

**Размер:** S · **Зависимости:** нет

**Зачем.** SPEC говорит «v2.0», но нигде не сказано, что именно обещано не ломать.
После M1–M3 в языке появится десяток новых имён, и без этого обещания встроенный
`morzebot` не сможет обновляться спокойно.

**Объём.** Раздел в SPEC: что стабильно (синтаксис, семантика D1–D19, имена стандартной
библиотеки, Go API `Value`/`Options`/`Interp`), что может меняться (текст диагностик,
внутренние пакеты `internal/`, производительность), правило депрекации (имя не удаляется,
а становится диагностикой did-you-mean — механизм уже есть, §19.2). Плюс `CHANGELOG.md`
и проверка `mzs --version` в CI.

## Чего в роадмапе нет и не будет

Это не пробелы, а решения — и они держат всё остальное:

- **Разделяемая память.** `async fn` даёт конкурентность без параллелизма (D19): ни
  блокировок, ни модели памяти. Ломать — значит заводить всё это.
- **Классы, наследование, `method_missing`, примеси.** T7 даёт форму данных, и хватит.
- **Макросы, перегрузка операторов, `eval`, `system`, рефлексия по типам Go.**
- **Диалекты и режимы совместимости.** Одна семантика (G3, §9).
- **Зависимости вне стандартной библиотеки Go** (I1) — из-за этого T15 сделан наполовину,
  и это правильная цена.
